# 四人错峰协调 case（2026-11-03）

复现：从 TCA 仓库运行 `uv run python scripts/run-staggered-case.py`。脚本在一次性目录中创建 SQLite 数据库、裸 Git 远程、四个独立工作树和真实提交；结束后自动清理。

| 到达顺序 | Claim 与协调 | 结果 |
| --- | --- | --- |
| A1，然后 A2（均未开工） | 同组动态审阅；M 把 `order_flow.py` 给 A1，把下游 `ingest.py` 给 A2 | 两者获准开工 |
| A3（A1 已开工） | 原 Claim 同时要改 `order_flow.py` 和测试；C 暂不放行，M 只指导 A3，A3 修订为只改测试 | A1 的执行中状态与修订号不受影响 |
| A4（独立） | 实现下游 `report.py` | 无须等待同组成员 |

运行结果：A3 的 Claim 有两版；四个工作分支完成本地 Git 核验、提交、推送，机械合并无冲突，合并后的功能测试通过，四个 Claim 均进入 `integrated`。脚本还构造一个未协调的 A3：从同一基线改写 A1 正在负责的函数，Git 合并在 `order_flow.py` 产生冲突。

**证据边界：**A、M 决策和代码内容由脚本预设；这验证协议状态、修订、Git 检查与机械集成，不验证模型能否自行找到正确契约，也不证明 TCA 比 solo 或 vanilla coop 更快。脚本输出的亚秒级时间只是程序执行时间，没有协作效率含义。下一步需要 3–5 个真实独立 Agent、多个错峰种子、相同任务的对照组，并统计集成成功率、返工次数与端到端时间中位数和长尾。
